# 第 2 课：可视化 —— `viewer.launch` 那一行背后发生了什么

> 对应代码：`robotics/02_view_panda.py`
> 前置：第 1 课
> 本课结束你能回答：渲染和物理是什么关系？为什么训练时必须关掉窗口？

---

## 0. 你写的那一行，其实启动了三个东西

```python
mujoco.viewer.launch(model, data)
```

这一行**会阻塞**，直到你关掉窗口。它内部同时跑着三件事：

| 谁 | 在干什么 | 频率 |
|---|---|---|
| **物理线程** | 不停地调 `mj_step(model, data)` | 由 `model.opt.timestep` 决定，这里是 500 Hz |
| **渲染逻辑** | 读 `data.xpos` / `data.xmat`，把每个 body 画成几何体 | 跟屏幕刷新率，通常 60 Hz |
| **窗口 / 输入** | 处理鼠标拖拽、滚轮缩放、UI 滑杆 | 事件驱动 |

**注意最重要的那点**：物理线程和渲染是**两个不同频率的东西**。物理每秒钟算 500 次，画面每秒钟只更新 60 次。

这就是为什么你看到机械臂在动，但仿真其实已经"走了"远多于你看到的帧数。

---

## 1. 渲染 ≠ 物理 ★ 本课唯一重点

这是一个初学者最常见的误解：

> ❌ 「窗口关了，仿真就停了」
> ❌ 「画面卡了，说明仿真算错了」

**真相是：渲染只是"读"物理算出来的结果，它不参与物理计算。**

```
物理线程：  qpos → [mj_step] → xpos, xmat   ← 真正的计算在这里
                                   │
                                   │ 只是读，不修改
                                   ▼
渲染逻辑：                把这些位姿画成一堆三角形
                                   │
                                   ▼
窗口：                          显示在屏幕上
```

推论：

1. **关掉窗口，物理计算完全不受影响**（只要你还在调 `mj_step`）
2. **渲染很慢，但物理可以很快**——这就是下一节的关键
3. **你没法通过"看"来判断仿真是否精确**。画面对不对，和数值对不对，是两件事

## 2. 为什么要 headless（无窗口）模式 ★ 工程上极其重要

在做强化学习训练时，一个 episode 可能要跑几千步，几十万个 episode。如果每一步都渲染画面：

- **速度会慢 10–100 倍**（渲染比物理计算贵得多）
- **你的 8 GB 内存机器会直接卡死**

所以训练时的标准做法是 **headless**：不画图，只算数。

```python
# 训练时的写法：没有任何窗口
for _ in range(10000):
    mujoco.mj_step(model, data)

# 想看效果时，才单独渲染几帧
renderer = mujoco.Renderer(model, height=480, width=640)
renderer.update_scene(data)
image = renderer.render()      # 得到一张 numpy 图像，可以存成 png
```

> **这就是为什么 `03_experiments.py` 里一张图都没有**——它只打印数字，跑一次 0.6 秒。如果它开窗口，你可能要等十秒。

**记住这个分界线**：

| 场景 | 要不要开窗口 |
|---|---|
| 学概念、调试数值 | 可以开，帮助建立直觉 |
| 跑训练、扫参数、批量实验 | **必须关**，用 headless + 存视频 |
| 演示、给别人看 | 开 |

## 3. `launch` 和 `launch_passive` 的区别（你现在不用管，但会碰到）

| 函数 | 谁在调 `mj_step` | 什么时候用 |
|---|---|---|
| `viewer.launch(model, data)` | **viewer 自己在后台帮你调** | 随便看看、演示 |
| `viewer.launch_passive(model, data)` | **你的代码自己调** | 你要写自己的控制循环、自己的 `mj_step` |

你写 02 时用的是 `launch`，所以机械臂会自己动（被重力拽着下沉）。

但等你后面写控制器（比如让末端走直线），就会换成 `launch_passive`：

```python
with mujoco.viewer.launch_passive(model, data) as viewer:
    while viewer.is_running():
        mujoco.mj_step(model, data)     # ← 你自己控制什么时候走一步
        viewer.sync()                    # ← 告诉渲染器"该重画了"
```

**为什么必须这样**：因为你的控制器要**在两步物理之间插入计算**。如果 viewer 自己在后台闷头 `mj_step`，你的控制信号根本没有插入的机会。

> 这是一个很典型的"控制循环"结构：**读状态 → 算控制量 → 施加控制 → 推进一步**。记下来，Stage 3 你会反复用到。

## 4. macOS 上的坑

| 现象 | 原因 / 解决 |
|---|---|
| 窗口打不开、闪退 | MuJoCo 用 GLFW 开窗口，macOS 上偶尔有兼容问题。确认你不是在无头环境（比如 SSH）里跑 |
| 窗口是黑的 | 显卡驱动 / OpenGL 上下文问题。Intel Mac 上是老版本 OpenGL，正常能用但不快 |
| `mujoco has no attribute 'viewer'` | 忘了 `import mujoco.viewer`（你已经踩过这个坑了）|
| 一开窗口机器就卡 | 你的机器 8 GB 内存 + 集显。关掉浏览器和其他重程序 |

**退路**：如果窗口实在打不开，用离屏渲染 `mujoco.Renderer` 存成图片/视频，**物理和数学部分完全不受影响**。别因为窗口问题卡住学习进度。

## 6. 小结

```
渲染和物理是两件独立的事：

  物理（mj_step） ──产出──→ xpos / xmat ──读取──→ 渲染 ──→ 屏幕
       ↑                                              │
    真正的计算                                    只是画出来

  · 关窗口不影响物理
  · 训练时必须 headless（否则慢 10~100 倍）
  · 要插入自己的控制逻辑 → 用 launch_passive，自己调 mj_step
```
